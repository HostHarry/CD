## 输入和模型前向

| 项目 | Native | VCD | VIGOR | CDAPC |
|---|---|---|---|---|
| 图像表示 | MAGVITv2 1024个码 | 同左；额外编码一次噪声图 | 同左 | 同左 |
| 输入布局 | 图像标记＋图像码＋聊天文本＋响应画布 | 同左 | 同左 | 同左 |
| 每轮模型前向 | 1次 | 2次，顺序执行 | 2次，probe_interval=1 | 2次，顺序执行 |
| 第二分支 | 无 | 仅把图像码换成噪声图的码 | 仅把图像码换成 MASK | token不变，用attention bias屏蔽非图像query访问图像key |
| 删除图像位置／缩短序列 | 否 | 否 | 否 | 否 |
| KV cache | 无 | 无 | 无 | 无 |
| 模型 logits | 全序列×全词表 | 同左 | 同左 | 同左，然后截取响应位置 |
| 概率处理 | 原生置信度 | 对比后FP64 softmax | 两分支FP64 softmax | 合法文本词表上的FP32 log-softmax等 |

模型全词表大小为 134656。CDAPC 当前每分支传给 proposal 的响应张量为
`[1, 256, 134656]`，其模型前向输入实际约1370个位置。
VCD/VIGOR 的模型同样对完整序列计算，未因只提交当前块而缩短前向输入。
VIGOR 中虽然存在 `cached_logits_noimg` 变量，桥接参数固定
`probe_interval=1`，每轮仍重新执行第二分支，不能将其当作缓存加速。

VCD 的图像加噪与第二次 MAGVIT 编码发生在预处理阶段，非每轮重复。
其 `decode_seconds` 不含这部分，`end_to_end_seconds` 包含。
CDAPC 的 `generation_seconds` 同样不含预处理；比较时应使用匹配的计时范围。

## 候选、排序与提交配额

| 方法 | 候选 token | 位置排序 | 提交配额 |
|---|---|---|---|
| Native | 正常分支 argmax | 正常分支候选概率 | 固定块中的计划配额 |
| VCD | `(1+alpha)*clean-alpha*noisy`，再以clean logits做候选过滤 | **过滤后对比分布中，所选候选的概率** | 保留固定块和计划配额 |
| VIGOR | 正常分支候选保持不变 | 同一候选的视觉增益 | 保留固定块和计划配额 |
| CDAPC | 合格时对比候选，fallback时base | u/r门控后按r、u排序 | 最左W个待填位置中最多K个；无合格位置时1个 |

VCD 的 APC 是作者的 adaptive plausibility constraint，即候选过滤，
并非本项目的 CDAPC 方法。当前参数为 alpha=1、beta=0.1、noise_step=500；
CDAPC 为 alpha=0.5、beta=0.1，且参考分支语义不同。

**更正之前的概括：** 这份 VCD 实现并非“由 clean 分支单独决定提交位置”。
`vcd/decode.py:39-47` 明确使用对比并过滤后的分布进行排序，
因此它同时可能改变候选 token 和提交顺序。

VIGOR 的实际作者公式为：

```
(p_img - p_masked)
+ log(clamp(p_img, min=1e-8))
- log(clamp(p_masked, min=1e-8))
```

它使用 clamp，非加 epsilon；也不同于 CDAPC 的
`r = pool_mass * q(candidate)`。VCD 的截断分布概率没有这个 pool_mass 因子。
这些机制差异可以影响排序和门控，但本次源码审查不将质量差额归因于其中某一项。

三种基线使用固定块边界；当前块未按计划处理完之前，不能不断补入后续块的候选。
已上传的 L256/T128 配置每轮计划提交2个位置。
CDAPC 的 W=16 是滚动的待填位置集合，K=4是上限，既非固定块也非固定2个配额。

## 为什么原候选 CDAPC 更容易慢

三个基线都能通过 `StopAtClosedPrefix` 在实际 EOS 前缀无 MASK 时停止。
这个包装器保留作者原有候选范围和块边界，不实施 CDAPC 的“已知EOS后只选前缀”规则。

固定块限制了尾部位置竞争：例如按 L256/T128/B64 的计划，
每块32轮、每轮2个位置；首块的前缀缺口不能因不断加入第2～4块位置而长期延后。
这是计划说明，不是对尚未导出的 think 运行轮数作实测断言。

CDAPC 原候选版则可能持续跳过前面的低分位置，把高置信度尾部填到很远。
本机4,769对相同输入的日志已直接证明：

| 指标 | 原候选＋安全EOS | EOS前缀候选 |
|---|---:|---:|
| 秒/输入 | 27.94 | 9.18 |
| 轮/输入 | 76.88 | 25.31 |
| 秒/轮 | 0.36338 | 0.36264 |
| 已知EOS后仅填尾部的轮次 | 66.22% | 0% |
| 可见输出token数 | 42.71 | 42.81 |

因此已证实原候选版的大量额外成本来自提交轨迹和尾部工作。
该证据不能把外部 think 的11.9秒与本机27.91秒的差额逐项分摊。

CDAPC 另外存在明确的工程工作量：对整个响应画布计算 proposal，再选W窗口；
Python逐标量排序；每个提交位置日志重复计算两次log-softmax、全词表排序取top-5。
这些操作位于生成计时内。基线也记录trace，并非没有日志；其提交记录主要是批量索引、
topk与列表转换。各项耗时占比尚未通过独立profile测定。

CDAPC 显式 attention bias 与基线默认全注意力可能触发不同的SDPA内核路径；
本次没有测运行内核，不能将“后端回退”作为已确认的耗时原因。
