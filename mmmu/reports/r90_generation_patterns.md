# MMMU r90 生成模式：提交顺序、尾部 EOS 与空推理

这是对已完成的 Native / CDAPC r90 / CDAPC r50 各 900 条记录的第二轮离线分析。重点是逐轮提交行为，没有重新推理、修改解码器或新增 judge 请求。统计来自相同的 900 道题；文本解码与已保存的评分文本逐条核对一致。

**主要发现：r90 同时存在过早提交 EOS、只留下空推理，以及 EOS 已出现后继续填尾部、让正文长时间等待的现象。多数 qualified 正文写入可以直接化简为视觉分支的置信度筛选；最终答案也经常早于部分推理正文被写死。**

## 1. 已知 EOS 后，9,834 轮只填尾部，前文没有推进

本统计在每轮开始时读取已提交的最早 EOS，仅当这一轮所有写入都在该 EOS 之后时，才计作“已知 EOS 后仅写尾部”。因此没有使用未来才知道的最终 EOS 位置来解释当时的调度。

| 指标 | r90 | r50 |
| --- | ---: | ---: |
| 有此现象的题目 | 658/900（73.11%） | 321/900（35.67%） |
| 仅写尾部的迭代 | 9,834/70,047（14.04%） | 2,873/28,237（10.17%） |
| 这些迭代中的 token 写入 | 72,729 | 35,385 |
| 其中写入 EOS | 72,729（全部） | 35,337 |
| 最长连续仅写尾部迭代 | 163 | 96 |

这不是 EOS 停止条件漏触发。此时前缀仍有未填位置，`eos_prefix_complete` 按定义还不能停止。

实现上的原因可以直接从调度逻辑和记录得到：

1. `choose_window()` 取最左 W=16 个未提交位置，没有在已知 EOS 处截断。
2. 当 EOS 前只有 1–15 个空位时，窗口会同时包含前缀空位和 EOS 后的空位。
3. EOS 后的位置很容易以极高置信度继续预测 EOS。
4. `choose_commits()` 只要在整个窗口找到任意 eligible 位置，就提交 qualified；仅在整个窗口没有 eligible 时才执行 fallback。
5. 结果是尾部 EOS 持续通过门控，阻止前缀空位进入 fallback。由于 K=W=16，本次这些纯尾部 qualified 轮中，窗口里的前缀空位确实没有 eligible 项被漏选。

相关实现：`src/cdapc_lab/decoding/window.py:choose_window`、`selection.py:choose_commits`、`engine.py:decode_cdapc`。

### 一个完整例子

`validation_Basic_Medical_Science_5` 最终只有 **92 个可见 tokens**，却用了 **239 步**，输出选项 A，judge 判对。下面使用从 1 开始的步数；原始日志 iteration 从 0 开始。

| 时间 | 实际行为 |
| --- | --- |
| 第 66 步 | 在位置 91 写入最终选项 A；尚有 14 个正文位置未填 |
| 第 67 步 | 在位置 92 写入 EOS；其前仍有 15 个未填位置，包括正文和格式位置 |
| 第 68–230 步 | **连续 163 步**，每步只在位置 93、94、…、255 写一个 EOS；前面的 15 个空位始终保留 |
| 第 231–239 步 | 尾部已经填完，才补完前缀 |
| 第 239 步 | 最后以 fallback 写位置 75 的 ` structure`，该位置的 r 约 0.635 |

此时“15 个前缀空位 + 1 个尾部空位”恰好填满窗口；尾部每写一个 EOS，就又进入一个新的尾部位置。这个轨迹展示了高置信尾部如何延后正文提交。

另一个样本 `validation_Public_Health_27` 只有 35 个可见 tokens，却用了 132 步；第 12–121 步连续 110 轮仅写尾部，每轮两个 EOS，前面的 14 个空位一直没有推进。

不能把这 14.04% 的迭代直接当作可无损删除的计算。模型使用双向注意力，在前缀仍未完成时改变尾部写入，会改变之后的前缀 logits，需要独立对照实验。

## 2. 正文和尾部受到的门控待遇差异很大

按最终输出位置划分 r90 的提交：

| 区域 | 总写入 | qualified | fallback | fallback 占比 |
| --- | ---: | ---: | ---: | ---: |
| 首个 EOS 前的可见文本 | 103,162 | 69,908 | 33,254 | 32.23% |
| 首个 EOS 本身 | 894 | 807 | 87 | 9.73% |
| 首个 EOS 后 | 92,013 | 91,568 | 445 | 0.48% |

正文约三分之一的 token 最终依赖 fallback。尾部则几乎全部通过门控。r50 的正文 fallback 比例为 6.03%，但它也仍有尾部排队现象。

更重要的是，r90 的 **69,908 个 qualified 正文写入中，66,880 个（95.67%）候选池只有一个 token**。这时有严格的代数关系：

```text
pool = {b}
c = b
q(b) = 1
pool_mass = p_visual(b)
r(b) = pool_mass × q(b) = p_visual(b)
```

所以对这些已接受的正文位置，r≥0.9 等价于视觉分支自身概率≥0.9，contrast gain 无法改变候选或 r 值。该性质已对所有保存的单候选池提交逐条校验。

这不意味着对比分支对全部调度无影响：多候选池位置、被拒绝的候选和 fallback 排序仍可能受影响。已接受的正文写入中有 2,886 次视觉 base 概率低于 0.9，却在实际对比分数下通过门控，说明对比计算确实改变了部分提交时机。

## 3. 最终文本的“推理→答案”排版不代表提交顺序

对有完整 `</think>`、其后出现明确选项字母、且能把该字母映射回原始 token 的题目：

| 指标 | r90 | r50 |
| --- | ---: | ---: |
| 满足此定位规则的题数 | 491 | 291 |
| 写答案时还有正文空位 | 343（69.86%） | 160（54.98%） |
| 答案写入后剩余正文空位，中位数 | 2 | 1 |
| 答案 token 由 fallback 写入 | 118 | 3 |
| 答案 token 相对同状态 base 被直接替换 | 3 | 46 |

r90 的典型过程允许先写末尾选项，再补齐前面若干推理 token；已提交的答案不会再被覆盖。这是双向扩散解码的实际提交顺序。

该探针只覆盖上述 491 道题，不代表其余题没有答案；答案也可能位于 think 内或使用选项正文表述。也不能由“答案较早写入”推导其推理必然错误：r90 中这组 judge 正确率为 110/343=32.07%，正文已完成后才写答案的组为 51/148=34.46%，属于事后分组，不能作为因果对照。

### 准确率与推理内容要分开看

`validation_Public_Health_27` 的选项是 A=5/19、B=5/18、C=5/17、D=5/20，gold 为 A。

- Native 正文写“Date of Event is 5/17”，末尾却写 A，judge 判对。
- r90 正文同样写 5/17，末尾写与之匹配的 C，judge 判错。

这个案例提醒我们：已有 judge 主要评答案，不能用它直接证明推理正文正确或正文与答案一致。

## 4. 80 条只输出 `<think>`；其中 12 条发生了换行→EOS

| 指标 | Native | r90 | r50 |
| --- | ---: | ---: | ---: |
| 归一化文本恰好为 `<think>` | 83 | 80 | 113 |
| 这些样本 judge 正确数 | 0 | 0 | 0 |

r90 这 80 条平均只运行 4.13 步，中位数 2 步，73 条的终止 EOS 由 qualified 提交、7 条由 fallback 提交。12 条的 EOS 是 **base 换行 → contrast EOS** 的实际替换，其余 68 条的终止 EOS 与同状态 base 一致。

例如 `validation_Geography_1` 的第 1 步就在位置 3 把换行改成 EOS；该 EOS 的原始视觉概率约 0.344，对比后的 r 约 0.908，最终只剩 `<think>`。

这说明对比替换也会影响是否开始输出正文。没有反事实续写，不能断言同状态下写回换行就一定能答对。

空输出也会拉低平均步数：r90 全体平均 77.83 步，剔除这 80 条空推理后，其余 820 条平均为 **85.02 步**。这只是描述性子集统计，不作为新的基准成绩。

把 `stop_rule` 改为 `fill_canvas` 不能恢复这些空答案：首个 EOS 已经被不可逆地提交，离线归一化仍会在同一位置截断。应检查 EOS 的候选与提交策略；当前提前停止逻辑本身符合其定义。

## 5. 高 r 值有时主要来自模板 token 的概率比

此前发现的 116 次开头 `"\n" → " The"` 替换，其统计为：

| ` The` 的指标 | 中位数 |
| --- | ---: |
| 原始视觉概率 p_visual | 0.2864 |
| 消融分支概率 p_ablated | 4.09×10⁻⁸ |
| gain = log(p_visual/p_ablated) | 15.68 |
| r | 0.9478 |

这里高 r 与消融分支把该开头词的概率压得极低有关，不能理解为“有 94.8% 概率识别对了图像事实”。这种模式和大量真实替换集中在开头格式、终止 token 的观察相符。

格式侧的总体对照：

| 文本特征 | Native | r90 | r50 |
| --- | ---: | ---: | ---: |
| 有 `</think>` 且后面有非空文本 | 455 | 616 | 415 |
| 有 `</think>`，其后为空 | 218 | 105 | 88 |
| 有 `<think>`，没有 `</think>` | 207 | 160 | 376 |
| 同一连续 8-token 片段出现至少 3 次 | 136 | 170 | 121 |

最后一行只是重复片段探针，会包含公式、重复题干等合法内容，且受长度影响；不能直接等同于幻觉或推理质量。r90 更常保留完整的“闭合 think + 后续文本”结构，但没有消除重复和空推理。

## 6. 下一步最值得验证的改动

优先做两个独立实验，保留当前 r90 作为对照：

1. **已知 EOS 后限制提交窗口到该 EOS 及其前缀。** 这样前缀没有 eligible 时就能进入 fallback，不必继续填尾部 EOS。这会改变尚未完成前缀的条件上下文，必须重新测答案质量和成本，不能声称输出必然等价。
2. **单独检查早期 EOS 的候选与提交。** 特别记录位置 3/4、think 尚未形成正文时的 base/contrast EOS 概率和门控。不要用延迟执行停止条件来代替对 EOS 提交本身的检查。

随后用 `timing_only_crossed` 隔离内容替换与调度作用，保留对比候选用于门控/排序、实际写回 base；再用 `gain_zero` 对照视觉置信度调度。这样才能判断收益来自内容替换、提交顺序还是格式变化。

增加最大步数不应排在前面：当前 r90 没有样本触及 256 步上限，长轨迹中的尾部排队也不会因更大的预算自动消失。

复现脚本：`scripts/mmmu_generation_patterns.py`。机器可读结果：`reports/mmmu_generation_patterns.json`，包含三组逐题摘要、选项提交探针以及三个代表样本的完整提交时间线。与前一轮审计脚本一样，需要原始项目环境和 run 文件；上传包保留代码和分析结果，不包含全部原始 predictions。
